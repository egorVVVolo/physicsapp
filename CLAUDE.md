# Physicsapp (рабочее имя) — правила проекта

Мобильное приложение с интерактивными уроками физики под **Edexcel International A Level, Unit 1 (WPH11)**.
Первый модуль — Kinematics. Полный план, scope и решения: **`docs/PLAN.md` — читать перед любой задачей.**
Почему приняты решения, что важно владельцу и что было в старом проекте: `docs/CONTEXT.md` (прочитать в первой сессии).
Как строить уроки (структура, типы шагов, визуализация, экзамен, шаблон, эталонный урок 2): **`docs/LESSON_FRAMEWORK.md` — обязателен перед работой над любым уроком.**
Как приложение выглядит, движется и звучит (цвета, движение, звук, ассеты, новые экраны, порядок внедрения): **`docs/DESIGN.md` — обязателен перед любой визуальной работой.**
Все функции приложения с фазами Pilot / MVP / Next / Later: `docs/FEATURES.md`.

## Владелец и общение
- Владелец — Егор, школьник A level, работает один, ~2 ч в неделю. Сильный в физике, разработчиком себя не считает.
- Общаться **по-русски**. Интерфейс, контент уроков, код и коммиты — **на английском**.
- Объяснять технические решения просто. Архитектура должна быть понятной, без лишних абстракций.
- Если владелец просит только обсудить или спланировать — ничего не реализовывать.

## Стек
- Expo (последний стабильный SDK) + TypeScript + Expo Router.
- Сцены: react-native-svg + Reanimated + Gesture Handler (Skia — только если M2 покажет проблемы с fps).
- В пилотной сборке — только библиотеки, которые работают в **Expo Go** (тестируем бесплатно). Для входа Apple/Google (после пилота) возможен development build.
- Контент — typed TS-файлы в `src/content/`. Прогресс — локально; после пилота синхронизируется через Supabase (анонимный аккаунт с первого запуска → привязка Apple/Google).
- Имя приложения — одна константа `APP_NAME`; нигде не хардкодить.

## Правила качества
- **Физика:** все числовые ответы вычисляются функциями из `src/physics/`, а не вписываются руками. Тест сверяет каждый ответ в контенте с моделью. Единицы обязательны.
- **Сцены:** движение по физической модели, стрелки привязаны к объектам, есть пауза/повтор/reduced motion. Анимация **не раскрывает ответ** до проверки.
- **Контент:** только оригинальные вопросы. Не копировать задания и тексты Pearson. Уровень по умолчанию — Intermediate (уровень экзамена). Не делать элементарщину.
- **Прогресс честный:** independent / assisted / revealed. Никаких выдуманных процентов mastery.
- **Дизайн:** перед новым экраном прочитать `docs/DESIGN.md` и использовать скилл/плагин `frontend-design`. Стиль «Brilliant + инженерный чертёж»: белая база, одна главная кнопка на экран, чертёж с меткой FIG, плоское 3D без градиентов. У каждого цвета один смысл: синий — сила и выбор, жёлтый — заработано, цвет уровня — где ты, зелёный и красный — только вердикт. Интерфейс не пружинит; пружинят только нарисованные тела, по формулам. Картинки рисуются кодом в `src/art/` (чужих и растровых ассетов нет). На экране один фокус: текст или чертёж. Нельзя: градиенты, glassmorphism, эмодзи-иконки, маскоты, конфетти, блёклые цвета, одинаковые сетки карточек, очки и лиги.
- **Доступность:** контраст ≥ 4.5:1, touch targets ≥ 44pt, смысл не только цветом.

## Как работать
1. Перед задачей, затрагивающей несколько файлов, — коротко описать план и дождаться «ок».
2. Работать в рамках текущего этапа (milestone) из `docs/PLAN.md`. Не расширять scope молча.
3. После визуальных изменений — проверить реальный экран (скриншот веб-версии / телефон) и показать владельцу. Прохождение тестов ≠ одобрение дизайна.
4. После каждого проверенного шага — **git commit** с понятным сообщением на английском.
5. Различать: идея / согласовано / реализовано / проверено. Не выдавать гипотезы за факты, не выдумывать отзывы и метрики.
6. После каждого завершённого шага — обновить раздел «Статус» ниже (коротко, без истории: где мы и какой следующий шаг). После `/clear` это единственная память о том, где остановились.
7. После каждого проверенного шага — `git push` в `origin main` (https://github.com/egorVVVolo/physicsapp). Владелец сам git не трогает.

## Владелец ничего не должен помнить — веди его сам
- Владелец не запоминает коды этапов (M1, M2…), команды и настройки. **Ты ведёшь процесс:** сам знаешь по разделу «Статус», какой этап и шаг следующий, и называешь их простыми словами («этап 1 — фундамент и выбор дизайна»).
- Если владелец пишет коротко («продолжаем», «го», «что дальше») — посмотри «Статус» и предложи следующий шаг.
- В конце каждого ответа, где что-то сделано, — одна строка «Дальше: …» и что нужно от владельца (например, «открой Expo Go и посмотри экран»).
- Когда от владельца нужно действие на компьютере или телефоне — давай точную инструкцию по шагам, а не просто название команды.

## Экономия токенов
- Модель — **Opus на high reasoning** (решение владельца 11 нояб.). Настройки в `.claude/settings.json` (`{"model": "opus", "effortLevel": "high"}`). Не менять без просьбы владельца.
- Открывать только нужные для задачи файлы; не читать `node_modules`, сборки и всю историю.
- Когда задача закончена и закоммичена — **напомни владельцу ввести `/clear`** (одной строкой: «Задача готова. Введи /clear, потом напиши "продолжаем"»). Контекст восстановится из этого файла и `docs/PLAN.md`.
- Если задача очень простая (переименование, текст, мелкая правка) — делай сразу, без режима плана.
- Если впереди особенно сложное решение (архитектура сцены, трудный баг) — предложи владельцу перейти в режим плана (Shift+Tab) перед началом.
